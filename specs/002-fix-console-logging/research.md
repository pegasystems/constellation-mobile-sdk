# Research: Shared SDK Console Logging

The updated specification resolves the public API, global-state, inspection-timing and common-facade decisions. No decisions remain open. The 2026-11-02 simplification replaces the Android output adapter and, per the subsequent user request, removes engine-local debug snapshots in favor of direct companion reads.

## Decision 1: Put the one mutable debug value and severity gate in `core.Log`

- **Decision**: Expose `ConstellationSdk.debuggable` as a companion property backed by a single default-`false` value in `core.Log`. Make the backing field volatile for Android/JVM and Kotlin/Native readers; evaluate the value at each attempted log emission rather than copying it into engines, handlers, or helpers. `Log` decides visibility for all SDK-native and forwarded native messages, including calls before any SDK instance exists.
- **Rationale**: The `core` module already owns `Log` and `ConstellationSdk`. A single field avoids duplicate state, repeated `if (debuggable)` checks, and passing logger objects through multiple layers. `kotlin.concurrent.Volatile` has an effect on Kotlin/JVM and Kotlin/Native backing fields ([Kotlin API](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.concurrent/-volatile/)); simple reads/writes suffice for a Boolean last-assignment-wins property. Verify this compiles on all project targets. Do not synchronize WebView inspection with changes to this value.
- **Alternatives considered**: Keep `InstanceLogger` with an engine-local flag (contradicts shared behavior); update all engine-owned logger instances when the companion property changes (requires registration/lifecycle tracking); put filtering only in Android/iOS handlers (misses `core.Log` and native helpers).

## Decision 2: Preserve native output behind one common facade

- **Decision**: Keep `core.Log` as the only facade with `v/d/i/w/e`, a private filter and internal `expect/actual` writers. Put native Android output in `core/androidMain`, not an engine adapter; iOS/JVM retain stdout formatting. Keep legacy String `i/w/e` and lazy routine-level overloads, but no lazy warning/error overloads or public output callback. Console handlers call the common methods directly.
- **Rationale**: Platform source sets already exist in core, so no Android API enters common code and no new dependency is required. Android WebView `LOG` maps to info and `TIP` to verbose; other native priorities, tags, error-source text and throwable traces remain intact. Common Android calls now also receive correct native severity/tag. iOS wire levels are defined in the existing `Console.js`: 1/2/3/4 mean error/warn/info/debug. Explicitly label level 4 DEBUG rather than preserving the old INFO mislabel. Capture actual output in tests instead of injecting a sink that bypasses production wiring.
- **Alternatives considered**: Retain the stateless engine adapter (correct but unnecessary layer); use stdout on Android (loses native metadata); rename public `Log` (unnecessary compatibility break); use only eager Strings (loses lazy suppression for request/event diagnostics).

## Decision 3: Read the companion property directly at existing engine operations

- **Decision**: Remove engine-local debug state and read `ConstellationSdk.debuggable` directly. Keep Android inspection at `configure`, Android embedded configuration at page load, and iOS inspection/embedded configuration at `performAction`. Recommend setting the property before SDK creation and not changing it mid-flow. This supersedes the earlier snapshot decision.
- **Rationale**: The user explicitly prefers one global value and does not expect mid-flow changes. Retaining a local copy only to stabilize that edge case is unnecessary. Existing lifecycle points and the serialized `debuggable` field remain unchanged; no JavaScript or synchronization code is needed.
- **Alternatives considered**: Keep a configure-time snapshot (unnecessary state for unsupported usage); retroactively synchronize all views on every setter call (unnecessary lifecycle complexity); remove the embedded configuration field (unrelated behavior change).

## Decision 4: Remove obsolete debug configuration interfaces and migrate all call sites

- **Decision**: Remove `ConstellationSdkConfig.debuggable` and the now-incompatible public `ConsoleHandler(showDebugLogs: Boolean)` constructor, as the user explicitly selected. Use one no-argument `ConsoleHandler` backed by `core.Log`; keep its registered `ConsoleScriptMessageHandler` and other public helper constructors unchanged. Migrate Kotlin and Swift samples, test fixtures, public guides, and `docs/ai/skills/cmp-app-integration/SKILL.md` away from the old argument. Swift's existing `ConstellationSdkCompanion().create(...)` pattern is the migration reference; verify that the new property is exported in the generated Swift interop before publishing Swift guidance.
- **Rationale**: Leaving a per-handler Boolean creates a second, misleading configuration surface. Removing the config property is a deliberate Kotlin/Swift source and binary break, including positional constructors, named arguments, destructuring/data-class `copy`, and framework consumers; leaving those call sites in samples would make the repo fail to compile. Record the break and migration in public documentation and the next release notes once a release version is selected.
- **Alternatives considered**: Deprecate and silently ignore the handler argument (misleading); have constructing a handler mutate the process-wide setting (hidden global side effect); preserve the per-instance config property (conflicting source of truth).

## Decision 5: Scope security and tests to observable native logging

- **Decision**: Keep forwarded custom-component messages on the shared SDK native-output policy. Leave independently emitted host-app logs (including sample code calling Android `android.util.Log` directly), app-provided resource-provider logs, WebKit's original console, and unforwarded browser utilities unchanged. Do not add or print authentication tokens, customer data, or new request payloads. Verify two-engine live native logging on Android and iOS through the manual smoke matrix. Separate simulated JVM logging, iOS engine-snapshot, and Android device logging tests were omitted at the user's direction. Tests touching the global property must reset it in `finally` or teardown to avoid contaminating other tests.
- **Rationale**: `Console.js` forwards log/info/debug/warn/error into the iOS handler *and* invokes the underlying WebKit console; filtering native forwarding cannot guarantee that browser inspector output disappears. The Android device regression previously captured Logcat for two engines and live toggles but was removed per user direction, so its scenarios require manual verification. The remaining iOS simulator handler test covers message-level mapping and global filtering; a compiler-only test cannot establish native-log output.
- **Alternatives considered**: Rewrite bundled JS to suppress the real WebKit console (out of scope); treat tests of the previous per-engine logger as evidence for the new global policy (invalid); indiscriminately reroute app-authored sample logging through the SDK gate (changes host-app behavior).

## Decision 6: Preserve sample settings; leave build-mode selection to consumers

- **Decision**: Per subsequent user feedback, restore the samples' previous explicit debug settings and remove the added build-mode plumbing. SwiftUI reads `Debuggable` from its plist; the other affected sample flows explicitly enable debugging. Remove the JVM logger test and shorten the companion property's KDoc.
- **Rationale**: Sample build-mode restrictions are not required for the central logging fix. Consumers needing debug-build-only logging can initialize the runtime flag from their own build setting; the SDK remains default-off and mutable.
- **Alternatives considered**: Keep the added sample `BuildConfig.DEBUG` / `#if DEBUG` selection (rejected by the user); infer application mode from the SDK library (wrong ownership).
